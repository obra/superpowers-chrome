The gap

PRI-3360, a follow-up to PRI-3319/#61. #61 taught auto-capture to refuse writing credential-shaped, data-sen-secret-marked, or known-sensitive-URL content to disk. It never touched the explicit, caller-requested readers -- eval, extract, attr -- which call straight into CDP and hand the result back to the caller with none of those checks. Real incident: a worker's eval/extract read Slack backup codes off a 2FA settings page (/account/settings/2fa_app) directly into its own run log, before the value was ever captured through the credential broker.

The fix

A page is now flagged sensitive by any of three independent signals: a known-sensitive URL pattern (the existing list in sensitive-url.js), a live data-sen-secret marker, or a new code-list density heuristic (skills/browsing/lib/code-list-detector.js: six or more distinct, similarly-sized alphanumeric tokens clustered together -- catches a recovery/backup-code list or bare-digit TOTP codes that have no fixed token shape, even on a page the URL list doesn't cover).

On a flagged page:

  • Every whole-page read is refused outright, before running: eval, a selector-less extract, extract/attr with a body/html selector, and the extract markdown branch (mcp/src/index.ts) -- the one path that built its own inline evaluate() call and was never routed through capture.js/extraction.js at all, so it had no sensitive-URL check before this.
  • Element-scoped reads stay allowed. extract/attr with a selector naming one real element still runs, but the resolved text is checked -- inside the tool, before anything returns -- against the same token-shape detector redactCredentialShaped already uses, plus the new code-list heuristic. A match refuses the whole read rather than redacting it: reading the text in-process to decide isn't the leak, returning it to the agent is. This is what keeps a value-blind check (did my code submit? what does the error banner say?) working on a sensitive page, which an unconditional whole-page refusal alone would have broken.
  • No new override, and the existing one was checked, not assumed. SUPERPOWERS_CHROME_ALLOW_CREDENTIAL_CAPTURE still gates this the same way it gates every other guard in the codebase. I checked how it reaches the running MCP server process rather than taking that for granted: it's read once from process.env at the moment each guard function runs, inside the already-started server. No use_browser action sets or exposes it -- the dispatch table has no such action -- and eval's expression argument runs in the browser page's own JS realm over CDP, a different OS process from the MCP server entirely, with no Node process global to touch in the first place. I added a test that drives this against a real Chrome: eval with payload: "typeof process" on a plain page returns "undefined", and an eval that would try to set the override on a sensitive URL is refused before it ever runs at all.

PRI-3337: Follow-up to PRI-3319/obra#61, which redacts secrets with a
recognized shape, id/name/class, or an explicit data-sen-secret mark.
None of that helps a secret revealed into a plain, unremarkable element
with none of those signals -- e.g. a "show password"/"reveal" click, or
the Google Admin console's reset-password flow rendering the generated
password into a bare div.Pv3Xyc. The very next auto-capture after such a
reveal would write it to disk in clear.

pause_capture/resume_capture (new use_browser actions) is the worker-
controlled answer: call pause_capture immediately before an action
expected to reveal a secret this way. Every automatic capture -- DOM
snapshot, markdown, screenshot, console-log placeholder, synthetic
dialog artifact -- is skipped for the rest of the session, with no CDP
call made to read the page at all, until resume_capture is called. The
triggering action itself still runs normally; only its capture is
skipped. An explicit `screenshot` action also refuses outright while
paused (with a message pointing at resume_capture) instead of silently
taking and discarding the shot. Pause state lives on the session and
persists across actions: forgetting to resume just means no more
captures for the rest of the session, never a silent leak.

Also: data-sen-secret-marked elements now have their whole text subtree
redacted in html-with-scrub.js/markdown.js, the same wholesale treatment
a pattern-matched secret container gets, instead of only having their
own value/data-*/aria-* attributes stripped. In the current pipeline the
whole-page credential-shape check already suppresses the entire capture
whenever a marker is anywhere in the top-level document, so this mainly
brings the two page-scripts' own redaction in line with that guarantee
for any caller that reads them directly.

jc review of #65 at 91d92d3: changes needed (one important false-positive problem)

The structure is right. Whole-page reads go through one gate (pageTextReadRefused: sensitive URL → marker → code-list density). Element reads are content-checked inside the tool and refused whole rather than redacted. The markdown branch, which never went through the gate before, now does. The override is honored inside the gate, and it really is unreachable from page JS. I checked that pageTextReadRefused short-circuits on credentialCaptureAllowed() itself, so running the gate before the override branch in extractText and getSanitizedHtml is fine.

1. [important] The code-list detector flags ordinary pages, and then eval and every whole-page extract are refused

I ran codeListDetected from this PR over document.body.textContent of real pages. I used each page's served HTML through the repo's jsdom, because textContent's handling of inline scripts is the same as in Chrome:

page body.textContent (what the gate reads) visible text only (script/style removed)
github.com//pull/65 FLAGGED clean
github.com/obra/superpowers FLAGGED clean
docs.github.com/en/rest/pulls/pulls FLAGGED clean
news.ycombinator.com FLAGGED FLAGGED
github.com/…/commits/main, en.wikipedia.org (OTP article), npmjs.com/package/react, stackoverflow.com question clean clean

There are two causes:

  • (a) Inline scripts. document.body.textContent includes <script>/<style> text. GitHub's embedded JSON (ids, hashes, UUID fragments) easily gives 6 or more distinct mixed alphanumeric tokens within 500 chars. Measuring visible text only fixes the three GitHub cases. Use innerText, or a clone with script,style,template,noscript removed, before textContent.
  • (b) The heuristic on visible text. HN's front page still trips it with scripts removed. Usernames and other short mixed tokens cluster like a code list.

Impact: on those pages eval is refused outright (it goes through pageTextReadRefusedForPs in evaluateWithCapture), and so is any selector-less, markdown, body or html extract. Agents use eval heavily on GitHub. Refusing it on an ordinary PR page is a larger regression than the accidental-capture risk this guards against. The design accepts false positives on whole-page reads because they "only force a narrower read", but eval has no narrower form.

Suggested fix: (a) is a one-liner and clearly right. For (b), either tighten the heuristic, or don't let code-list density alone refuse eval. For example, apply density only to extract, or require density together with a sensitive-looking cue on the page. Add the four flagged pages above as negative fixtures, saved HTML, to code-list-detector.test.mjs, alongside the existing positive corpus.

2. [minor] isWholePageSelector only catches the literal body/html

:root, html > body, body:not(.x) and * (whose first match is <html>) all resolve to the whole document but count as element-scoped. So they skip the URL and marker gate and get only the content check. On a /2fa setup page, a bare base32 setup key matches no token shape. I suggest deciding in-page instead: resolve the element and treat it as whole-page when el === document.documentElement || el === document.body. That covers every selector spelling. A wrapper like #app still counts as element-scoped, which is consistent with the design.

Checked and fine

  • The marker check and ancestor walk still run on element reads, and the content check runs after them.
  • location.href is read in page JS, but location is unforgeable on window.
  • The behavior change (whole-page reads now refuse instead of stripping) is documented in the CHANGELOG, and the 6 changed tests match it.
